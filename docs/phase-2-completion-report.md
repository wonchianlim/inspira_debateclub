## 1. 一句话结论

Phase 2 交付了完整的**管理端**：超级管理员可以管理用户与角色、审批裁判与维护赛制资格、维护系统设置、
查看审计日志；俱乐部管理员可以创建/编辑/克隆活动、设置活动赛制、推进活动状态、发布通知。

每一次特权改动都**自动留痕**（数据库触发器，与业务写入同一事务），
状态流转有**穷举测试覆盖的状态机**，时间换算有**覆盖夏令时的时区逻辑**，
并且所有关键约束在**界面与数据库两层**各自验证。

## 4. 决策与偏差

### 4.1 新增的架构决策

| 编号 | 内容 |
|---|---|
| [ADR-0013](./decisions/0013-audit-via-triggers.md) | **审计日志由数据库触发器写入，而不是由应用代码写入** |

### 4.2 与计划的偏差（均已记录理由）

| 偏差 | 原因 |
|---|---|
| **P2-2 没有创建 `lib/audit/` 模块** | 计划要求在应用层写审计函数，但 Supabase 的 JS 客户端每个请求各自一个事务，"改数据 + 写审计"是两次请求，**无法保证原子性**。改为数据库触发器后应用代码不再写审计，因此没有可写的模块。详见 ADR-0013 |
| **P2-4 未实现"匿名化"** | SCHEMA-D-2 要求"停用 + 匿名化"，本阶段只做了**停用**。匿名化要同时处理 `profiles` 的个人字段与 `auth.users` 的邮箱/凭据，属破坏性操作，需要独立的设计与确认流程。界面已明确标注尚未实现 |
| **P2-7 状态机只在应用层强制** | 不加数据库触发器，避免把跳转规则写两份导致漂移；而"绕过应用直接改状态"在本系统里没有可行路径（浏览器从不直连数据库，有自动检查守着） |
| **P2-9 不做任意键值编辑器** | 只提供已知设置项的类型化表单。任意 JSON 编辑更容易把系统写坏，且后果会在别处（"新建活动"）才暴露 |
| **P2-10 额外实现了审计日志查看页** | 审计日志的价值在于能读。入口页原本承诺 P2-10 提供，因此补齐 |

### 4.3 被否决的做法

- **不用 Redis 或中间件做限流**（Phase 1 已否决，Phase 2 沿用）。
- **不把活动状态跳转规则写进数据库**（见上）。
- **不在通知中心重复受众判断**：能读到什么完全由 RLS 决定；应用里再写一份既不安全也会漂移。
- **不在 `/events` 页把"隐藏草稿"当成安全边界**：那只是呈现选择，页面注释已写明。

## 6. 关键技术决策与其理由（供后续阶段参考）

1. **审计用触发器而非应用代码** —— 原子性无法在应用层保证；触发器还拦得住绕过应用的直连改库。
2. **敏感字段按列名模式遮蔽且递归处理嵌套 jsonb** —— 将来新增的列只要名字含 `email`/`phone`/`token`/`secret` 就自动被覆盖，不需要记得改审计代码。
3. **领域逻辑集中且可穷举** —— 状态机 81 组合、裁判可指派性 48 组合全部穷举测试。混入数据库访问就再也做不到。
4. **时区换算自己实现并覆盖夏令时** —— 不引入第三方库；只做一次偏移修正的实现在切换日会错一小时。
5. **`event_date` 不由管理员填写** —— 由开始时间推导，避免"北京凌晨的活动日期差一天"。
6. **时间偏移量存数据库不写死代码** —— 产品负责人改时间安排不需要改代码、不需要重新部署。
7. **状态流转"先判断再写入"** —— 并有源码级测试守住这个顺序（挪到写入之后所有功能测试仍会通过，但数据库已留下非法变更）。
