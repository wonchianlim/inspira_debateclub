## 4. 决策与偏差

### 4.1 一处**产品负责人提出、我采纳并替换了原设计**的改动

原计划是"提供一个函数，让已报名的学生看到本活动参与者的姓名 + 学校名单，再从名单挑人"。
我按计划实现并测通之后，产品负责人建议：**给每个学生一个编号，配对时直接输入编号找人**。

**这个建议更好，我采纳了，并把原设计删掉。** 理由：

| | 浏览名单 | 搭档码 |
|---|---|---|
| 默认情况 | 同场**任何人**都能看到全部参与者的姓名与学校 | **只有对方把码告诉你**，你才能找到他 |
| 码未泄露时 | — | **没人能找到你** |

保留"浏览名单"等于把刚关上的门重新打开，因此那个函数被**删除**而不是并存。

**一个缺了就前功尽弃的前提：搭档码必须随机生成，不能是连号。**
若做成 `S0001`、`S0002`……，任何人顺序试就能枚举全部学生。因此实现为 10 位随机码
（32 个易读字符，约 1.1×10¹⁵ 种），并排除易看错的字符（0/O、1/I/L）。

### 4.2 其他决策

| 决策 | 理由 |
|---|---|
| 报名规则在**应用层与数据库各写一份**，并加**跨层一致性测试** | 两份规则必须一致，否则会出现"界面说能报名、数据库却拒绝"。db-tests 发现不了"只有应用层被改了"，因此额外加了一条**直接读迁移 SQL 源文件**比对的单元测试 |
| 活动状态用**排除法**而不是列举法 | 将来新增状态时，排除法只会少允许，列举法会**静默多允许**一种 |
| 搭档请求的前端**只提交码，不提交学生 id** | 否则就绕过了"必须知道对方的码"这个前提 |
| 查找函数返回字段加**显式隐私断言** | 它是 SECURITY DEFINER，返回什么完全由代码决定；不加断言的话，将来有人顺手加一列就会把学生的评分或邮箱公开，而**没有任何测试会失败** |
| 撤销函数的 `PUBLIC` 执行权 | PostgreSQL 默认把新建函数授予 `PUBLIC`，不撤销的话 `anon` 实际就能调用 |
| 偏好保存用"先清后写" | `preference_rank` 有唯一约束，逐条更新在调整顺序时会中途撞约束 |

### 4.3 被否决的做法

- **不放宽 `student_profiles` 的 SELECT 策略让学生互看** —— 策略是行级的，一放开整行都能读（含运营备注）。改用列级的最小暴露。
- **不让管理员的人工操作受截止时间限制** —— 管理员本就是在处理异常情况，应由他直接指定状态。
- **不用连号学生编号**（见 4.1）。

## 7. 跨层一致性：这是本阶段最值得保留的做法

Phase 3 出现了一个新问题：**同一条业务规则被写在两个不同的层里**
（应用层纯函数 + 数据库函数/策略）。两边漂移的后果是
"界面说能报名、数据库却拒绝"，用户看到一句英文错误。

目前有两道防线：

1. **db-tests 里的「报名窗口与活动状态」一节**：逐个活动状态建活动、调用数据库函数，
   与一份期望清单比对 —— 它能发现**数据库函数被改了**。
2. **单元测试里的跨层断言**：直接读迁移 SQL 源文件，与应用层清单比对 ——
   它能发现**只有应用层被改了**。

两者都做过反向验证（故意改一边，测试确实失败）。
