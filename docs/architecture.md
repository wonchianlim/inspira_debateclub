## 1. 文档目的

本文回答四个问题：

1. 这个系统由哪些部分组成，它们之间怎么通信；
2. 哪些代码运行在**浏览器**里，哪些运行在**服务器**上（这条决定了安全性）；
3. 数据库和登录功能怎么接、怎么保证权限不被绕过；
4. 部署成什么形态，以及在大陆访问这条硬要求下有哪些明确约束。

---

## 2. 名词先解释（面向非技术读者）

| 名词 | 通俗解释 |
|---|---|
| Next.js | 一个用 JavaScript/TypeScript 写网站的框架。它可以把一部分代码放在服务器上运行。 |
| App Router | Next.js 的组织方式：每个文件夹/文件对应一个网址页面。 |
| React 组件 | 页面的一块界面。 |
| 服务端组件（Server Component） | 在服务器上运行、只把结果发给浏览器的组件。适合"读数据"。 |
| 客户端组件（Client Component） | 在浏览器里运行的组件。适合需要点击、输入等交互的地方。 |
| Server Action | 一段"只在服务器上执行"的函数，浏览器点按钮时触发。权限检查放在这里。 |
| 数据库迁移（migration） | 一个记录"数据库结构怎么变"的文件。按顺序执行，可以重建整个数据库。 |
| RLS | Row Level Security，行级安全。数据库自己判断"这一行数据你能看吗"，即使程序写错了也拦得住。 |
| JWT | 一张由服务器签发的"身份凭证"，证明你是谁。 |
| service-role key | 数据库的"万能钥匙"。**绝对不能**出现在浏览器里。 |
| 幂等 | 同一个操作点两次，结果和点一次一样，不会产生重复数据。 |

## 3. 总体架构

系统是**一个** Web 应用，不是微服务。规范第 1.2 节明确排除微服务。

```text
                        用户（学生 / 裁判 / 教练 / 俱乐部管理员 / 超级管理员）
                                        │
                                        │ HTTPS，只访问我们自己的域名
                                        ▼
                    ┌───────────────────────────────────────────┐
                    │   自有域名（例如 app.inspira-xxx.com）      │
                    │   Alibaba Cloud 或 Tencent Cloud           │
                    │   香港 / 新加坡 区域（Phase 0 测试后确定）    │
                    └───────────────────────────────────────────┘
                                        │
                            ┌───────────┴───────────┐
                            ▼                       ▼
                    ┌───────────────┐      ┌──────────────────┐
                    │ Next.js 应用   │      │ 定时任务容器       │
                    │ （Docker 容器） │      │ （cron，发邮件）   │
                    └───────┬───────┘      └────────┬─────────┘
                            │                       │
                            └───────────┬───────────┘
                                        ▼
                    ┌───────────────────────────────────────────┐
                    │  PostgreSQL + 认证（Supabase 或同区域替代） │
                    │  数据库、RLS、认证数据、文件存储             │
                    └───────────────────────────────────────────┘
                                        │
                                        ▼
                              邮件服务商（投递到中国大陆邮箱）
```

**关键点：** 浏览器**不直接**访问数据库、认证服务或邮件服务商。所有请求先到我们自己的域名，由服务器转发。这样做的原因是规范第 5.4 节：大陆访问不能依赖境外的第三方域名，而认证是最关键、最不能失败的一步。

> 说明：这个"浏览器只访问自有域名"的目标来自规范第 5.2 节。第 7 节说明具体怎么做到。

## 4. 技术栈与版本策略

### 4.1 已确定的技术栈（来自规范第 5.1 节）

| 层 | 选型 |
|---|---|
| 应用框架 | Next.js App Router |
| 语言 | TypeScript，开启 `strict` |
| 界面 | React、Tailwind CSS、shadcn/ui |
| 服务端接口 | Next.js Server Actions 与 Route Handlers |
| 数据库与认证 | PostgreSQL + 托管 Supabase（新加坡区域）**待 Phase 0 连通性验证后确认** |
| 授权 | 数据库 RLS + 服务端权限检查（双重） |
| 输入校验 | Zod |
| 单元/集成测试 | Vitest |
| 界面测试 | React Testing Library |
| 端到端测试 | Playwright |
| 代码质量 | ESLint、Prettier、TypeScript 编译器 |
| 部署 | 可复现的 Docker 镜像，运行在香港或新加坡的 Linux 服务器 |

### 4.2 版本策略

规范第 5.1 节要求"使用初始化时最新的、互相兼容的稳定版本，并锁定在 lockfile 里"。

具体做法：

- 初始化时用当前稳定版（`next`、`react`、`@supabase/ssr`、`zod` 等），把精确版本写进 `package.json`，并把 `package-lock.json` 提交进仓库；
- **不使用** `^` 或 `~` 范围（避免不同机器装出不同版本）；
- 依赖升级必须单独提交、单独验证，并重新跑大陆连通性测试（规范第 14.5 节）；
- 新增任何运行时依赖前，必须先做大陆可访问性检查并取得产品负责人同意（规范第 5.1 节、第 1.2 节）。

> 精确版本号在 Phase 1 初始化时填入。Phase 0 不锁定版本，因为 Phase 0 不写应用代码。

### 4.3 包管理器（需要产品负责人确认）

**建议使用 `npm`。** 理由：

- 这台电脑已经装好 `npm`（随 Node.js 一起装），不需要额外安装全局工具；
- `package-lock.json` 能完整锁定版本，满足规范要求；
- 对非技术负责人来说，出问题时 `npm install` 是最容易在网上找到答案的命令。

备选是 `pnpm`（DSH 内置了一份）。如果以后想换，从 `npm` 换到 `pnpm` 是机械操作，不会影响架构。

## 6. 服务端 / 客户端边界

这是整个架构里最重要的一节。规范第 7 节要求"权限在数据库和服务端执行，客户端路由守卫只是可用性层，不是安全"。

### 6.1 规则

| 规则 | 说明 |
|---|---|
| R1 | 默认用**服务端组件**读数据。客户端组件只用于确实需要交互的控件。 |
| R2 | 所有**写操作**都在 Server Action 或 Route Handler 里执行。 |
| R3 | 每个写操作**先**做权限检查，**再**动数据。两次检查：应用层 `requireCapability()` + 数据库 RLS。 |
| R4 | 浏览器端组件**不得**导入任何带 service-role 的模块。 |
| R5 | 领域逻辑（配对算法、ballot 校验等）放在 `lib/domain/`，**不得**写在页面组件里，这样单元测试可以直接调用。 |
| R6 | 页面组件只负责取数、展示、把用户操作转交给 Server Action。 |
| R7 | 客户端路由守卫只用来改善体验（例如隐藏菜单），**不作为**安全依据。 |

### 6.2 为什么每条写操作都要两次检查

- **应用层检查**给出友好的错误信息，并且能表达"工作流状态"这类 RLS 难以表达的规则（例如"比赛已开始，名单不能改"）。
- **数据库 RLS** 是最后一道防线：即使某个 Server Action 忘了检查，或者将来有人加了新的查询路径，数据库仍然会拒绝。

只要少了任何一层，都可能出现越权。规范第 14.3 节要求测试**主动尝试**越权操作，就是为了验证第二层真的存在。

## 7. 数据库与认证客户端模式（核心决策）

Supabase 提供三种客户端。用错一种就会绕过 RLS，因此这里明确定义每一种的用途。

### 7.1 三种客户端

| 文件 | 用什么 key | 运行在哪 | 权限 | 用途 |
|---|---|---|---|---|
| `lib/supabase/server.ts` | anon key + **当前用户的登录凭证** | 仅服务器 | **受 RLS 限制**，身份 = 当前用户 | **默认**。所有读、所有业务写。 |
| `lib/supabase/admin.ts` | **service-role key** | 仅服务器 | **绕过 RLS**（万能） | 极少数确实做不到的操作，见 7.3。 |
| `lib/supabase/client.ts` | anon key | 浏览器 | 受 RLS 限制 | 默认不用。仅当以后需要实时订阅时才引入。 |

### 7.2 默认路径

所有业务数据访问都走 `lib/supabase/server.ts`。这样 RLS 自动按"当前登录用户"生效，不需要在每个查询里手写权限过滤——这也正是规范第 7 节"授权在数据库边界实现"的落地方式。

### 7.3 service-role 的允许用途清单

只有以下情况可以使用 `lib/supabase/admin.ts`，且每处都要有明确注释说明为什么不能用用户身份完成：

1. **投递邮件**：`email_jobs` 的出队与状态更新（定时任务没有登录用户）。
2. **创建认证账号**：Super Admin 代建用户时，Supabase Auth 的管理接口需要 service-role。
3. **系统级初始化**：种子数据、迁移后的回填。

**禁止**：为了"省事"绕过 RLS；在 Server Action 里用 service-role 代替权限检查。

技术上用 `server-only` 包保证：如果有人在客户端组件里 import 了 `lib/supabase/admin.ts`，**构建会直接失败**，而不是等到上线才发现密钥泄漏。

### 7.4 会话刷新

`middleware.ts` 在每次导航时调用 `supabase.auth.getUser()` 刷新会话 cookie。

必须使用 `getUser()`，**不能**用 `getSession()` 做授权判断——后者读取 cookie 内容，可以被伪造；前者会向认证服务核实。

## 8. 认证流程与"只访问自有域名"策略

规范第 5.4 节禁止生产页面依赖未经大陆测试的境外域名，第 5.2 节要求浏览器尽量只访问自有域名。认证是**每个用户每次使用都要走**的路径，因此最需要处理。

### 8.1 做法：认证调用全部经 Server Action

| 操作 | 实现位置 | 浏览器是否直连认证服务 |
|---|---|---|
| 注册 | Server Action | 否 |
| 登录 | Server Action | 否 |
| 登出 | Server Action | 否 |
| 忘记密码 | Server Action | 否 |
| 重置密码 | Server Action | 否 |
| 会话刷新 | `middleware.ts`（服务端） | 否 |

浏览器只向 `我们的域名` 发请求，服务器再与认证服务通信。这样即使认证服务从大陆访问不稳定，登录页本身仍然能打开，也便于我们统一记录和排查问题。

> 代价：登录请求多了一跳（浏览器 → 我们的服务器 → 认证服务）。这会让登录稍慢一点，但换来的是可控性和可测试性。这是有意的取舍，会写入 ADR。

### 8.2 邮件链接必须回跳自有域名

Supabase 默认的"重置密码"邮件链接指向 Supabase 自己的域名。这会造成两个问题：域名不属于我们，且可能在大陆打不开。

因此必须：

1. 在认证服务里把邮件模板的链接改成 `{NEXT_PUBLIC_APP_URL}/auth/confirm?...`；
2. 实现 `app/auth/confirm/route.ts`，在自有域名上完成验证并建立会话；
3. 在认证服务的"允许跳转地址"白名单里只放自有域名。

这一步没做，重置密码功能在大陆就等于不可用。**必须在 Phase 1 完成，并纳入大陆连通性测试。**

## 9. 数据访问与领域逻辑

- 数据库类型由 Supabase CLI 生成（`supabase gen types typescript`），提交进仓库，保证 TypeScript 能发现字段名写错。
- 每个领域模块在 `lib/domain/<领域>/` 下导出一组函数，输入经过 Zod 校验，输出是明确的类型（不是 `any`）。
- 页面组件不直接写 SQL，也不直接拼查询；调用领域函数。
- 规范第 5.2 节要求"领域逻辑与页面渲染分离"，这条纪律是后续单元测试能覆盖配对算法的前提（规范第 10.8 节、第 14.2 节）。

---

## 10. 输入校验

- 所有来自浏览器的输入（表单、Server Action 参数、Route Handler 请求体、查询字符串）都必须经过 Zod 校验。
- Zod schema 集中在 `lib/validation/`，**服务端和客户端共用同一份定义**，避免两边规则不一致。
- 校验失败返回安全的用户提示，不返回数据库错误原文。
- 规范第 7 节还要求：不把用户填写的文本（通知、ballot 评语）当 HTML 渲染，避免 XSS。

## 11. 事务与幂等

规范第 5.6 节要求多行操作使用数据库事务，重要操作尽量幂等。

### 11.1 用数据库函数保证原子性

以下操作写成一个 PostgreSQL 函数（在 Supabase 里通过 RPC 调用），要么全成功，要么全失败：

| 操作 | 为什么需要事务 |
|---|---|
| 确认配对（写 teams + team_members + participations.status） | 多张表必须一致 |
| 移动参赛者 | 同上 |
| 开始辩论（写 roster 快照 + 更新 matches 状态与时间） | 快照和状态必须同时成立 |
| 提交 ballot | ballot + ballot_scores + ballot_feedback + matches 状态 |
| 发布 ballot | ballot + matches + 通知入队 |

### 11.2 幂等的实现方式

- **报名**：`registrations` 上的 `UNIQUE (event_id, student_id)` 约束是最终防线。重复点击得到"已报名"，而不是两条记录。
- **签到**：更新 `checked_in_at` 时用 `WHERE checked_in_at IS NULL`，重复点击不改变已有时间。
- **开始辩论**：函数内检查 `started_at IS NULL`，第二次调用返回既有状态。
- **提交 / 发布 ballot**：基于 `ballot_status` 的状态机判断，非法状态直接拒绝。
- **邮件**：`email_jobs.dedupe_key` 唯一约束（规范第 12 节）。

约束（constraint）是"最后一道防线"这一角色，来自规范第 5.6 节。

## 12. 审计

规范第 6.7 节和第 7 节要求 `audit_logs` 只追加、任何应用角色都不能改或删。

设计：

- 审计写入封装在 `lib/audit/`，也被数据库函数直接调用；
- 数据库层面**不**给任何应用角色 `UPDATE`/`DELETE` 权限（通过 RLS 与权限授予双重限制）；
- 每次写入包含 `actor_profile_id`、`entity_type`、`entity_id`、`action`、`old_value`、`new_value`、`request_id`；
- 必须审计的动作清单（规范第 6.7 节）：评分、资格、角色授予、队伍、比赛名单、裁判指派、手工签到、比赛结果、ballot 重开/重提/发布、复核处理。

`request_id` 把一次用户操作和它的多条审计记录、日志串起来，方便事后追查。

## 13. 邮件与定时任务

规范第 12 节要求 11 类邮件，并要求：邮件失败**不能**回滚业务操作。

### 13.1 生产与消费分离

```text
业务动作（事务内）
   └─ INSERT INTO email_jobs (status='pending', dedupe_key=..., scheduled_for=...)
        │  ← 邮件只是"登记待发"，此时事务已可提交
        ▼
定时任务（每分钟）
   └─ POST /api/jobs/dispatch-email  （带密钥头）
        └─ 领取若干条 pending → 调用邮件服务商 → 更新为 sent / failed
```

因为入队和业务动作在同一个事务里，而真正的发送在事务之外，所以邮件服务商出问题不会影响报名、发布等业务操作。

### 13.2 可靠性要求

- 领取任务时用 `FOR UPDATE SKIP LOCKED`，避免多实例重复发送；
- 记录 `attempt_count` 与 `failure_reason`；
- 超时未完成的 `processing` 记录必须可被回收重试；
- `dedupe_key` 唯一约束防止重复发送；
- 失败在管理员界面可见、可重试（规范第 12 节）。

### 13.3 调度器（需要产品负责人确认）

规范排除了队列和后台服务，且生产不用 Vercel，因此**没有现成的定时器**。建议：在 Docker 部署里加一个 `cron` 容器，与主应用共用同一个镜像，每分钟调用一次上面那个受保护接口。

这样做的代价是多一个容器；好处是不引入外部调度服务、不增加大陆访问依赖，且完全在自有服务器内。

## 14. 错误处理

- 领域层返回明确的结果类型（成功或带错误码的失败），**不**抛出含义不明的异常。
- 禁止"吞掉错误"（规范 `AGENTS.md` 的 Code Quality 规则）。每个捕获处必须要么处理、要么向上传递。
- 给用户的是安全的中文提示；给运维的是不含个人信息的诊断信息。
- 界面必须为每个主要页面设计：加载中、空、错误、无权限、成功五种状态（规范第 13 节）。
- 未授权访问返回 403 或跳转，且**不泄漏**"这条记录是否存在"（规范第 8 节）。

## 15. 可观测性

规范第 5.4 节要求监控位置也要记录在数据位置清单里。

- **日志**：结构化 JSON 输出到标准输出，由 Docker 收集。**禁止**记录电话号码、邮箱内容、认证 token、ballot 内容（规范第 7 节）。
- **请求关联**：每个请求生成 `request_id`，写入日志和 `audit_logs.request_id`，出错时可以在界面上展示给用户，方便定位。
- **健康检查**：`GET /api/health` 返回应用状态与数据库连通性，供云平台探活使用。
- **错误追踪服务**：规范第 5.1 节禁止未经批准新增运行时依赖。是否需要 Sentry 一类的错误追踪服务，属于待确认事项（见第 19 节），需要产品负责人批准，并确认其数据存放地区。

## 16. 环境变量

依据规范第 5.3 节，并补充本架构新增的两个。

| 变量 | 用途 | 可见范围 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 数据库/认证服务地址 | 浏览器可见 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 匿名 key（受 RLS 限制） | 浏览器可见 |
| `SUPABASE_SERVICE_ROLE_KEY` | 万能钥匙 | **仅服务器** |
| `RESEND_API_KEY` | 邮件服务商密钥（服务商待定） | **仅服务器** |
| `EMAIL_FROM` | 发件人 | 仅服务器 |
| `NEXT_PUBLIC_APP_URL` | 自有域名，用于邮件回跳 | 浏览器可见 |
| `JOB_DISPATCH_SECRET` | 定时任务调用接口的共享密钥 | **仅服务器** |

规则：

- 仓库里只提交 `.env.example`（只有变量名，**没有**真实值）；
- `lib/env.ts` 在服务端启动时用 Zod 校验必需变量，缺失就直接启动失败（避免上线后才发现配置漏了）；
- `NEXT_PUBLIC_` 前缀的变量会被打包进浏览器代码，**永远不要**把密钥放进去；
- 真实密钥只存在服务器环境与本地 `.env.local`（`.env.local` 必须写进 `.gitignore`）。

## 17. 部署形态

- **镜像**：多阶段构建的 `Dockerfile`，使用 Next.js `output: 'standalone'` 产出精简运行镜像；以非 root 用户运行；`NODE_ENV=production`。
- **运行单元**：`docker compose` 两个服务——`app`（对外）与 `cron`（内部定时任务），共用同一镜像。
- **数据库**：托管 Supabase（新加坡）或同区域托管 PostgreSQL，**待 Phase 0 连通性验证后决定**（见 `docs/deployment-regions.md`）。
- **区域**：应用计算必须实际运行在香港或新加坡的明确区域（规范第 5.4 节）。
- **域名与证书**：自有域名 + HTTPS，且证书链在大陆可正常校验。
- **静态资源**：CSS/JS/图标/字体全部由应用自身提供，自托管字体。生产页面**不得**加载 Google Fonts、公共 CDN、Google Analytics、reCAPTCHA 等未经大陆测试的资源（规范第 5.4 节）。
- **备份**：数据库备份策略与存放位置必须写入数据位置清单。

## 18. 时区

规范第 5.5 节：

- 所有时间戳用 `TIMESTAMPTZ` 以 UTC 存储；
- 展示时按事件自身的 `timezone` 渲染，V1 默认 `Asia/Shanghai`；
- 迟到取消、预警、逾期的判断**全部基于时间戳**在服务端计算，不使用浏览器本地时间的假设。

这条很重要：如果客户端时钟不准或用户改过时区，基于浏览器的判断会出错。

## 19. 需要产品负责人确认的架构问题

以下问题会实质影响数据模型、权限或成本，按规范第 0 节和第 17 节，不能由实现者自行决定。

| 编号 | 问题 | 建议默认值 | 影响 |
|---|---|---|---|
| A-1 | 包管理器用 `npm` 还是 `pnpm`？ | `npm` | 影响后续所有命令，容易更换 |
| A-2 | 应用界面用什么语言？（规范只规定与负责人沟通用中文，未规定应用界面语言） | 中文界面 | 影响所有文案与 i18n 结构，越早定越好 |
| A-3 | 是否需要错误追踪服务（如 Sentry）？其数据存放在哪个地区？ | 暂不引入 | 影响监控与数据位置清单 |
| A-4 | 邮件服务商最终选哪家？ | Phase 0 投递测试后决定 | 影响投递成功率与成本 |
| A-5 | 定时任务用同镜像的 `cron` 容器是否可接受？ | 接受 | 影响部署复杂度 |
| A-6 | 注册后新用户的默认角色是什么？（规范未说明，见 `docs/decisions/`） | 默认 `student` | **影响 RLS 策略与 Phase 1 认证流程** |
| A-7 | 数据库与认证最终方案（托管 Supabase 新加坡 / 同区域托管 PostgreSQL / 自托管）？ | 待连通性验证 | **影响 schema 与迁移成本，必须在 Phase 1 前确定** |
