## 4. ⚠️ 本阶段最有价值的部分：测试抓出的**四个真实缺陷**

四个都不是靠读代码发现的，是测试直接失败暴露的。

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | 候选池要求"**同一轮**里凑够人数"才算可行 | 同样愿意去某赛制、但填在不同志愿位的人**永远凑不到一起**，三个人全都打不上 | 单元测试直接失败 |
| 2 | 候选人**同时留在多个赛制的池子里** | 一个人被分配到**两个赛制**（4 个学生产生 8 条参与记录）；下游比赛与评分表都会错 | 单元测试 + 调试打印 |
| 3 | 给搭档种子补位时，剩余池子**仍包含种子成员自己** | 产生 `["s1","s1","s2"]` 这种**同一人出现两次**的队伍，人数看起来还对 | 单元测试直接失败 |
| 4 | 生成服务**忽略每个查询的错误** | 一次外键失败表现为"**生成出 0 支队伍**"，看起来完全像算法问题，排查方向被带偏数轮 | 集成测试 + 逐层排查 |

**缺陷 2 与 3 都补了专门的回归测试，并做了反向验证**（去掉修复后确实失败）。

---

## 5. ⚠️ 两种"假通过"，以及为什么反向验证是必须的

### 5.1 一条**假通过**的回归测试

缺陷 3 的回归测试最初用的是 PF(2 人一队) / WSDC(3 人一队) 的场景。
**这个场景根本触发不了这个缺陷** —— 去掉修复后 WSDC 的池子里只有 2 人、仍不到 3 人，
缺陷不显现，**回归测试照样全绿**。是**反向验证**这一步把它抓出来的。

> **教训：光写回归测试不够，必须确认"去掉修复它就会失败"。**

### 5.2 一条**无效**的对照测试

我想用"换个传入顺序"构造交叉分组来对比成本，但算法内部会先按评分排序 ——
**传入顺序根本影响不了结果**（那正是确定性所要求的）。两边算出来一模一样（24 对 24）。
改成用成本函数手工算出交叉分组的成本，才是有意义的比较。

### 5.3 又一次"空表假通过"

新表 `pairing_proposals` 的拒绝对应用例一开始**全部通过** —— 但那是因为**表里没有数据**。
0 行既可能是"权限拦住了"，也可能是"本来就没有行"。是管理员那条 `allow` 用例返回 0 行才暴露的。

**这个模式在 Phase 3 与 Phase 4 一共出现了三次**（P3-1 子查询取 NULL、P4-1 发言位没占用、P4-5 空表）。
共同点是：**测试通过的原因和它想验证的事情无关。**

## 6. 决策与偏差

### 6.1 对计划的调整

| 调整 | 原因 |
|---|---|
| `match_cost`（规范 10.4）从 P4-2 **推迟到 Phase 5** | 规范第 15 节把"比赛与正反方提案"放在 Phase 5，而 Phase 4 只产出**队伍**提案。按"不提前建设后续阶段"的要求推迟 |
| P4-6 拆成"先生成流程验证、再界面"两步 | P4-5 报告里明确标注了生成流程"尚未端到端验证"，先补上再往上盖界面 |

### 6.2 规范没有定义、我**没有**替产品做决定的地方

| 情况 | 做法 |
|---|---|
| "搭档组人数**大于**一支队伍"怎么办 | 规范没写。保留能凑成的完整队伍、其余的人回到普通池子，并**明确警告让管理员处理** —— 不擅自决定"留下谁" |
| 补位时评分差距过大 | 如实提示"搭档优先于评分相近，但这会影响比赛质量"，**不假装**这条搭档队伍"评分相近" |
| `team_cost` 公式里各项的**单位** | 规范给了公式但没逐项定义。明确写出来并做成**显式输入**（人数类=几个人、`incomplete_team`=布尔、标准差=总体标准差），避免实现者各自理解 |

### 6.3 关于"全局优化"的边界（写在代码注释里，不含糊）

规范说"全局优化而不是贪心"，但同时明确"V1 uses a transparent **deterministic heuristic**"。

严格意义上的全局最优（在全部学生 × 全部赛制上求最优）是指数复杂度；
"选总成本最低的**互不重叠**候选组集合"是**集合划分问题**（set packing），一般情形下 NP 难。

因此实现的是"**候选池跨轮累积 + 可行性判定 + 补位**"的启发式，
利用问题本身的结构（评分项在按评分排序后按连续窗口分组时达到最优；
已接受搭档是硬性优先项，先锁定再补位）。

**代码注释与提案说明里都写明：不保证数学意义上的全局最优**，而不是含糊宣称"已全局优化"。

### 6.4 其他决策

| 决策 | 理由 |
|---|---|
| 跨表不变式用**触发器**而不是应用代码 | "一个参与最多在一支未解散队伍里"与"队伍/参与的活动赛制一致"是跨表约束，CHECK 做不到；一旦出错，下游比赛与评分表都会错且很难发现 |
| 队伍状态变化时**也**重新检查成员 | 把已解散队伍改回提案状态时，成员可能已在别的队伍里 —— 那一瞬间就会出现"一个人在两支活队伍里" |
| 提案**输入快照不含个人信息** | 只存学生 id、评分、资格、可用性、搭档与历史队友；姓名/邮箱能通过 id 关联出来，再复制一份只会多一处需要保护的个人信息 |
| 提案与队伍**分开存** | 队伍是**当前状态**，提案是**一次生成的历史**；混在一起会导致同一批输入重复存 N 份，且无法表达"这一次生成整体如何" |
| 解散用**状态标记**而不是删除记录 | 外键与"最多在一支未解散队伍"的触发器都以状态为准；删除会丢掉历史，审计里的删除记录也失去对照对象 |
| 警告**分两类**并放在页面**最上方** | 混在一起管理员分不清"必须处理"与"看过就行"；管理员看不到说明，规范"说明取舍"的要求就等于没实现 |
| 锁定**同时标记** `manually_edited` | 规范保留"已锁定**或**人工调整"的分配，而锁定本身就是一次人工判断 |

## 9. 跨层一致性

Phase 4 把 Phase 3 建立的两道防线继续用上了：

- 成本函数的**每个权重**都有独立测试（把该项加 1，断言总成本恰好增加该权重）；
  另有一条**整表比对**测试，任何一项被改动都会立刻失败。反向验证过：改错一个权重 → 3 条测试失败。
- 算法版本号 `PAIRING_ALGORITHM_VERSION` 已就位。任何影响结果的改动**必须**递增它，
  否则历史提案会出现"同一个版本号对应两套算法"，变得无法解释。
