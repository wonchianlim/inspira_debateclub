## 2. 五种赛制的官方模板（**全部来自产品负责人**）

| 赛制 | 分制 | 队伍总分 | 特征 |
|---|---|---|---|
| `ONE_V_ONE`（即兴辩论） | 正反方各 30（5 维） | 30 | 按队伍打分 |
| `JWSD` | 每人 100 + 回复 50 | 350 | 前三位整数、回复允许半分 |
| `WSDC` | 每人 100 + 回复 50 | 350 | 同 JWSD；主发言者硬限 **60–80** |
| `PF` | 每人 30（5 维、允许半分） | 60 | 不允许平局与低分获胜 |
| `BP` | 每人 **60–85**（整数） | — | **四队排名**；名次与分数不一致只警告 |

**这些内容我一条都没有编。** 全部来自产品负责人给的规范，
并各自有**可执行的断言**（见下方测试清单）—— 将来若有人改错满分、
漏掉一个维度、或把"总分自动计算"改成手填，测试会失败。

## 3. 评分表 schema 的七项能力

| 能力 | 为哪个赛制加的 |
|---|---|
| 按学生 / 按队伍 / 整场 三种作用范围 | 全部 |
| **可重复列表**字段（含"+ 添加 / 删除"） | 1v1、JWSD、WSDC、PF、BP |
| **结构化列表条目**（每条带子字段） | JWSD、WSDC、PF（裁判笔记、交锋三段笔记） |
| **分数分档标签**（让裁判看到每档含义） | 全部（裁判信心） |
| 文字**建议**字数（软）与**上限**（硬） | 全部 |
| **计算总项**（不存数据库） | 全部 |
| **只对某些发言位次生效**的字段 | JWSD、WSDC（回复发言者） |
| **排名字段**（值分布多队且互斥） | BP |

### 总项有三种汇总方式

- `team`：把该队伍自己的若干字段相加（1v1 的 30 分）
- `speaker`：把该学生自己的若干字段相加（JWSD/WSDC 的 100 分、PF 的 30 分）
- `teamFromSpeakers`：把队员的个人总分相加（JWSD/WSDC 的 350、PF 的 60）

### 硬规则与软警告是**两条路**，刻意分开

| | 进 `issues`（**阻止提交**） | 进 `warnings`（**仅提示**） |
|---|---|---|
| 用途 | 缺项、超区间、不允许低分获胜、不能平局、队伍分差越界 | 分数异常高/低、理由过短 |
| 可覆盖 | **否** | 是 |

**这个区分是从规范原文推出来的，不是我自己定的**：1v1 §20、PF §49 明确要求
"不要因为写作质量阻止提交"；而 PF §3、§48 明确要求低分获胜"不可覆盖"。
两者的措辞差别（"recommended" vs "must"）决定了它们是不同的东西。

### 几条值得单独说的测试

**跨层一致性（ballot-lifecycle）。** 状态机同时写在 TypeScript 与数据库函数里。
只写在应用层，任何绕过应用的写入都能把草稿直接改成已发布；
只写在数据库层，界面无法知道该显示哪些按钮。因此两处都写，
并有一条测试**直接读迁移文件**比对两边的转换清单 —— 反向验证过：
改 TS 会让 4 条失败，改 SQL 会让 2 条失败。

**假通过（vacuous pass）。** "数据库拒绝非法 schema"那条测试最初通过了，
但通过的原因是 `created_by` 为空，**与 schema 完全无关**。
补上之后插入成功了 —— 数据库原本接受数组。
为此新增了两条 check 约束，并让测试检查错误码是 `23514`，
确保是约束拒绝而不是别的原因失败。

**不要空跑成假通过。** 模板存取测试里有一条 `expect(insertedTemplateIds.length).toBeGreaterThan(0)` ——
否则"所有赛制都查不到"会让循环一条也不测就通过。

## 5. ⚠️ 我在本阶段犯过的错（都记在这里，而不是删掉）

| 错误 | 怎么发现的 |
|---|---|
| 假通过：数据库拒绝非法 schema 其实是因为缺 `created_by` | 补上 created_by 后插入成功了 |
| 算术错：30 与 27.5 误算成合计 51.5（实为 **57.5**） | 测试断言失败 |
| 测试数据错：把"按队伍"的论点放进了整场 | 测试报"在 team-prop 上没有填写" |
| 规则加错赛制：队伍分差规则落到了 1v1 上（文案与 JWSD 几乎相同） | 跨模板测试 |
| `guidance` 落错模板：WSDC 的评分参照表被放进了 JWSD | 跨模板测试报"WSDC 的 guidance 未定义" |
| 分数分配辅助函数把余数塞给满分最小的项，算出 5.5/2 分 | 测试报"超出上限" |
| `minLength` 当成硬要求 → 短理由被拒绝提交 | 测试期望"有警告且能提交"，与实现相反 |
| 同一文件里重复声明 `teamFields` | 类型检查 |
| 未使用的导入 / 常量 / 参数（多次） | lint（`--max-warnings=0`） |
| 测试名里的英文双引号导致 TS 解析失败（**多次**） | 类型检查 |

**其中"假通过"与"把建议当成硬限制"这两类最危险** ——
它们不会报错，只会让系统在错误的地方放行或拦截。

## 7. 还没有做的事（如实列出）

1. **`guidance` 评分参照表还没有显示在裁判填表页上。**
   数据已经在模板里（WSDC 的 60–80、BP 的 60–85），但界面还没渲染。
   规范明确要求它"在打分时始终可见"。
2. **裁判填表是单页，不是规范里的 6–7 页向导。**
   功能上所有字段都能填，但流程没有分步。
3. **学生的复核请求（`ballot_review_requests`）还没做界面。**
   表与 RLS 已就位（P7-1），但学生还不能提交复核请求。
4. **超时提醒只有页面标记，没有真发邮件。**
   因为没有邮件服务商（待确认项）。逻辑是完整的，接上服务商即可。
5. **BP 的名次与分数不一致只有硬性区间，没有那条软警告。**
   BP 规范第 33 节要求给出"第一名分数明显低于第四名"的提示，目前尚未实现。
6. **`ballot_scores` 里 BP 的排名字段不落库** ——
   排名存在 `ballots.format_data`（JSONB）里，与列表字段同样处理。
   这是可以的，但需要说明：SQL 层无法直接对排名做约束，
   约束在应用层（`checkValueType`），并有测试覆盖。
