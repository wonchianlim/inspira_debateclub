# ADR-0013：审计日志由数据库触发器写入，而不是由应用代码写入

- 状态：已接受
- 日期：2026-09-29
- 相关：规范第 15 节 Phase 2（"Audit all privileged mutations."）、第 6.7 节、第 7 节；
  `supabase/migrations/20260929091600_audit_triggers.sql`

## 背景

Phase 1 建好了 `audit_logs` 表，并做了三重保护（无 UPDATE/DELETE 策略、显式 REVOKE、客户端无 INSERT），
但**没有任何代码往里写**。Phase 2 要求"所有特权改动都要审计"，因此必须决定**由谁来写**。

`docs/phase-2-plan.md` 的 P2-2 原计划是"在 `lib/audit/` 下实现服务端函数，供各特权动作调用"。
实际实施时发现这个做法有一个无法回避的缺陷。

## 决定

**改由数据库触发器写入**，应用代码不负责写审计。

## 理由

### 1. 应用侧写入**不可能**保证原子性

Supabase 的 JavaScript 客户端**每个请求各自一个事务**。因此"先改数据、再写审计"是两次 HTTP
请求、两个事务。必然存在两个失败窗口：

| 情况 | 后果 |
|---|---|
| 改数据成功、写审计失败 | 改动**没有留痕** —— 审计出现空洞 |
| 写审计成功、改数据失败 | 记录了一次**没有发生**的改动 —— 审计说谎 |

而规范要求审计是可信的。审计里出现空洞或假记录，比没有审计更危险，因为它会让人**误以为**有完整记录。

触发器在**同一个事务**里执行，要么都成功、要么都回滚，从结构上排除了这两种情况。

### 2. 触发器**无法被忘记**

应用侧写入依赖"每个新增的特权写操作都记得调用审计函数"。这是一条**靠自觉**的约定，
而人会忘记。将来有人加了一条更新活动状态的路径却忘了写审计，测试也可能照常通过。

触发器挂在表上，新增代码路径**自动**被覆盖。

### 3. 触发器拦得住"绕过应用"

如果有人直接改数据库（运维手改、脚本导入），应用侧审计完全看不到；
触发器照样留痕。

### 4. 审计范围是"表级"的，正好对应"特权改动"

需要审计的是对特定表的增删改。触发器天然以表为单位，与需求形状一致。

## 具体做法

- `audit_row_change()`：通用触发器函数，`SECURITY DEFINER`、固定 `search_path`；
- 用 `AFTER` 而不是 `BEFORE`：这样看到的是 `set_updated_at` 等 BEFORE 触发器处理之后的**最终值**；
- 挂在 12 张表上：`profiles`、`user_roles`、`student_profiles`、`judge_profiles`、
  `student_format_profiles`、`judge_format_qualifications`、`debate_formats`、`format_positions`、
  `events`、`event_formats`、`notices`、`system_settings`；
- **不**挂 `audit_logs` 自己（会无限递归）；
- **不**挂 `registrations` / `registration_format_preferences`：那是学生自助操作，不是特权改动（Phase 3 范围）。

### 敏感字段遮蔽

规范第 7 节要求日志不得包含手机号、邮件内容、token、选票内容；AGENTS.md 另外要求不得记录个人邮箱地址。

做法：按**列名模式**（`email` / `phone` / `mobile` / `password` / `token` / `secret` / `api_key`）
匹配并**替换值为 `[已隐去]`，但保留键**。

- 保留键的价值：审计里仍然看得出"这个字段被改过"，只是看不到内容。
  若直接删掉键，"改了邮箱"这件事会从审计里彻底消失。
- 用模式匹配而不是固定清单：**将来新增的列**只要名字带这些词就会被自动覆盖，不需要记得改审计代码。
- **递归**处理嵌套结构：`system_settings.value` 是 jsonb，敏感值可能藏在里面。

### 变化检测

两个细节，都是实测踩出来的：

1. 判定"是否真的有变化"必须用**原始值**，不能用遮蔽后的值。
   若只改了邮箱，遮蔽后两边都是 `[已隐去]`、看起来一样，会被误判成"没变化"而**整条漏记**，
   等于"改邮箱不留痕"。
2. 比较时必须**排除 `updated_at`**。`set_updated_at` 触发器每次都会刷新它，
   若算进比较，则"保存了但什么都没改"也永远被判定为有变化，审计表会被无意义记录塞满。

## 影响

**变简单：**
- 各 Server Action 不需要写审计代码，也不会忘记写；
- 原子性由数据库保证，应用层不需要事务编排（Supabase JS 客户端本来也做不到）；
- 审计范围一目了然：看触发器挂在哪些表上即可。

**变复杂 / 代价：**
- 审计逻辑在 SQL 里，不如 TypeScript 直观，修改需要写迁移；
- 每次写操作多一次触发器执行（可忽略）；
- 操作者来自 JWT（`auth.uid()`）。使用 service-role 或直接连库时操作者为 `NULL`，
  这类"系统操作"记为空操作者而不是伪造成某个人 —— 这是**如实记录**，不是缺陷；
- 未来若需要"某次批量操作算一个整体"，需要额外机制（本阶段没有这种需求）。

## 备选方案

1. **应用侧在 Server Action 里写审计。** 原子性无法保证，且靠自觉。否决。
2. **为每个特权动作写一个 SECURITY DEFINER 存储过程，内部同时改数据并写审计。**
   原子性可以保证，但每个动作都要写一个函数，且应用必须改成调用 RPC，
   同时仍无法覆盖"绕过应用直接改库"。成本更高、覆盖面更小。否决。
3. **逻辑复制 / CDC 到外部审计系统。** 超出 V1 范围，且引入额外依赖。否决。

## 待确认

- 无。若将来发现某张表不该被审计（例如高频写入的临时表），
  去掉对应触发器即可，不影响其它表。
