# ADR-0012：应用层频率限制采用数据库固定窗口计数器

- 状态：已接受
- 日期：2026-09-29
- 相关：规范第 7 节、第 6.7 节；`lib/auth/rate-limit.ts`、迁移 `20260929091400_rate_limiting.sql`

## 背景

主规格第 7 节要求："Rate-limit authentication-adjacent, review-request, and email-trigger endpoints."（对认证相邻、复核请求、邮件触发的接口限流。）

需要保护的两个入口：

- **登录**：防止针对某个账号或某个来源的密码暴力破解；
- **找回密码**：防止被当作邮件轰炸工具（顺带保护域名信誉，避免被邮件服务商判为垃圾发信方）。

既有条件：Supabase Auth 自身带有限流，本地配置为 `sign_in_sign_ups = 30 次/5 分钟/IP`、`email_sent = 2 封/小时`。因此问题不是"完全没有保护"，而是**要不要在更前面再加一层**。

## 决定

### 1. 在应用层增加一层，位于调用认证服务**之前**

两层并存、互不替代：应用层负责在压力传导到认证服务之前挡住，认证服务层作为兜底。

### 2. 计数存在数据库，不放在进程内存

进程内计数器有两个问题：重启即清零；多实例部署时各自为政，攻击者只要让请求落到不同实例就能绕过。放进数据库，限制才是全局有效的。

### 3. 采用固定窗口，而不是滑动窗口

`window_start = floor(epoch / window_seconds) * window_seconds`。实现简单、行为可预测。

**已知代价：** 固定窗口在边界处理论上允许两倍瞬时流量（窗口末尾用满、下一窗口立刻再用满）。对"防暴力破解与邮件轰炸"这个目的而言可以接受；若将来需要更平滑的限制，可在不改调用方接口的前提下换成滑动窗口或令牌桶。

### 4. 同时按 IP 与邮箱两个维度计数

- 只按 IP：攻击者换 IP 就能继续猜某账号的密码；
- 只按邮箱：攻击者用一个 IP 遍历大量邮箱，变成撞库。

两者叠加才能同时挡住"盯住一个账号"与"广撒网"。

### 5. 数据库只保存加盐哈希，不保存明文 IP

计数键由**应用侧**用 `RATE_LIMIT_SALT` 做 SHA-256 后传入。这样：

- 数据库里没有可直接识别的个人信息（`AGENTS.md` 的隐私要求）；
- 即使数据库被读取，也无法用彩虹表反推 IP（盐不在数据库里）。

盐因此成为一个**必需的**服务端环境变量（至少 32 字符，可用 `openssl rand -hex 32` 生成）。

### 6. 时间取 `clock_timestamp()`，不取 `now()`

`now()` 返回**事务开始时间**，在同一事务内多次调用不会变化。这在实际请求中通常没问题（每次请求各自一个事务），但会让行为依赖调用方的事务边界，且无法在单个事务内测试窗口推进。

实测发现了这一点：把"跨窗口后应重新计数"写成测试时，由于 `DO` 块整体是一个事务，`now()` 始终不变，窗口永不推进，测试失败。改用 `clock_timestamp()` 后行为与墙钟一致且与事务边界无关。

### 7. 限流本身出错时**放行**（fail-open），并记录错误

取舍理由：

1. 数据库不可用时，登录本来也会失败，限流失效不会让情况更糟；
2. 认证服务自身仍有一层限流，不会因为这里放行就完全失去保护。

若将来要求更严格，可改为 fail-closed，但必须同时准备好告警，否则限流组件一抖动就会把所有人挡在门外。

### 8. 取不到来源 IP 时跳过限流并告警

本地直连 `next start` 时 `x-forwarded-for` 通常不存在。若强行用一个固定的"未知"键，所有开发流量会挤进同一个桶，反而更难用。

**因此这是一条部署要求：** 生产环境必须运行在会设置 `x-forwarded-for`（或 `x-real-ip`）的反向代理之后，否则应用层限流会被静默跳过（会打印警告）。

## 影响

**变简单：**
- 限额与窗口集中在一处（`RATE_LIMITS`），调整无需改调用方；
- 计数与判定在一条 SQL 语句内完成，并发安全（不会出现"两个请求都读到 0 于是都放行"）；
- 数据库里不含明文 IP。

**变复杂：**
- 多了一个必需的环境变量（`RATE_LIMIT_SALT`），配置漏了会导致启动失败（这是刻意的）；
- 计数器会累积，需要定期清理（已提供 `prune_rate_limit_counters`，保留 7 天）；
- 固定窗口的边界效应（见第 3 点）。

## 备选方案

1. **只依赖认证服务自带的限流。** 保护存在，但压力已经传导到下游；且我们自己的接口没有任何拦截，成本更高。未采用。
2. **进程内存计数器。** 重启清零、多实例失效。否决。
3. **引入 Redis 之类的限流中间件。** 规范第 5.1 节要求不引入无必要依赖，且会增加一个境外依赖点（对大陆访问不利）。否决。
4. **直接存明文 IP。** 简单，但属于存储个人信息。否决。

## 待确认

- 无。限额取值（登录 10 次/5 分钟、找回密码 5 次/小时）属于可调整的实现细节，若实际使用中出现误伤，可直接调整 `RATE_LIMITS`。
