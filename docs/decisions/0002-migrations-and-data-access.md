# ADR-0002：结构变更只走迁移；数据访问分三种客户端

- 状态：提议
- 日期：2026-09-29
- 相关：规范第 5.2、5.6、7 节；`docs/architecture.md` 第 7 节；`docs/schema.md` 第 5 节

## 背景

规范第 0 节要求"所有数据库变更都使用迁移，绝不做未记录的仪表盘改表"。规范第 7 节要求 service-role 密钥"仅在服务端、范围狭窄、绝不作为绕过授权的捷径"。

这两条要求回答的是同一个问题的两面：**谁有权改变数据库，以及以什么身份访问数据。**

## 决定

### 1. 结构变更

- 所有表结构、索引、策略、函数都写在 `supabase/migrations/` 里的有序迁移文件中；
- 生产数据库**禁止**通过网页控制台手工改表；
- 每次变更都必须能从空数据库一次性重放成功（规范第 16 章）；
- 数据库类型定义由 CLI 生成并提交进仓库，使 TypeScript 能在编译期发现字段名错误。

### 2. 三种客户端，职责固定

| 客户端 | key | 身份 | 用途 |
|---|---|---|---|
| `lib/supabase/server.ts` | anon + 用户会话 | 当前登录用户 | **默认**。全部业务读写。 |
| `lib/supabase/admin.ts` | service-role | 超级身份（绕过 RLS） | 仅限三种用途，见下 |
| `lib/supabase/client.ts` | anon | 浏览器中的用户 | 默认不用 |

### 3. service-role 的允许用途

只有：投递邮件（定时任务无登录用户）、代建认证账号、系统级初始化。每处必须注释说明为什么不能用用户身份完成。

用 `server-only` 包做技术保证：客户端组件若 import 了 admin 模块，**构建直接失败**。

### 4. 权限测试禁止使用 service-role

因为 service-role 绕过 RLS，用它做权限测试会得出"全部通过"的假象。测试必须以各角色的真实身份连接。

## 影响

**变简单：**
- 数据库结构可从零重建，环境之间可复现；
- 默认路径天然受 RLS 保护，不需要在每条查询里手写权限过滤；
- service-role 的使用点极少，代码审查容易覆盖。

**变复杂：**
- 改表需要写迁移文件，不能"图快"在控制台点几下；
- 需要维护生成的类型定义（每次迁移后重新生成）；
- 需要本地 Supabase 环境来跑迁移与权限测试。

## 备选方案

- **直接使用服务端 ORM 并以超级身份连接。** 会绕过 RLS，使规范第 7 节的"权限在数据库边界执行"落空。未采用。
- **不做迁移，依赖手动 SQL 脚本。** 无法保证"从空数据库重建"，违反规范第 16 章。未采用。

## 待确认

无。本条是实现纪律，不需要产品负责人做取舍，批准 Phase 0 即视为接受。
