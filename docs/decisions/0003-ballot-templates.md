# ADR-0003：Ballot 采用共享表 + 按赛制版本化模板

- 状态：已接受（2026-09-29 经产品负责人确认）
- 日期：2026-09-29
- 相关：规范第 6.6 节、第 2.10 节、第 10.4 节、第 17 节；`docs/schema.md` S-13、S-14

## 背景

系统支持五种赛制（PF、JWSD、WSDC、BP、ONE_V_ONE），每种赛制的 ballot 字段、分值范围、胜负判定方式都不同。规范第 6.6 节明确要求："不要创建五套互不相关的 ballot 系统。使用共享表加版本化的按赛制模板。"

## 决定

采用**三层结构**：

1. **`ballot_templates`** — 每个赛制一个版本化的 JSON 结构定义，描述该赛制的必填字段、字段类型与校验规则。模板是**配置**，不是数据仓库。
2. **`ballots`** — 共享主表，保存比赛、裁判、所用模板版本、状态机、胜负、理由、以及一份 `format_data` JSONB 补充数据。
3. **`ballot_scores` / `ballot_feedback`** — 结构化的分数与文字反馈，可被查询与统计。

配套约束（补充规范第 6.6 节）：

- 每个赛制**只能有一个启用版本**：`CREATE UNIQUE INDEX ... ON ballot_templates (format_id) WHERE active;`
- 分数类型改为查找表 `ballot_score_types`，使每个赛制的分数上下限有存放位置，而不是散落在代码里。

## 影响

**变简单：**
- 新增赛制主要是加数据（模板 + 位置 + 分数类型），不需要新建五套表；
- 修改某赛制 ballot 只影响该赛制，且旧模板仍可用于历史比赛；
- 分数与反馈是结构化数据，可以做统计与历史查询。

**变复杂：**
- 需要设计并维护 JSON 模板的结构校验（避免"模板写错导致裁判无法提交"）；
- 模板 JSON 的字段定义**必须由产品负责人提供**，这直接阻塞 Phase 7；
- 四队赛制（BP）不能用单一"胜负"表达。`ballots.winner_team_id` 对 BP 允许为空，结果以 `match_teams.placement` 表达（规范第 10.4 节）。

## 备选方案

1. **每个赛制一张独立表。** 被规范第 6.6 节明确否决。
2. **把整份 ballot 内容作为一个大 JSONB 存储。** 实现最快，但分数无法被索引、统计或做范围校验，历史查询会变困难。否决。
3. **把模板字段做成完全的关系型表。** 校验能力最强，但对一个非技术负责人维护的产品来说过于复杂。折中为"JSONB 模板 + 关系型分数"。

## 待确认

- **五种赛制各自的 ballot 字段、分值范围、总分与胜负规则**（规范第 17 节列为待确认，`docs/schema.md` D-7）。这是 Phase 7 的硬前提。
- 谁有权限维护 ballot 模板？（`docs/permissions.md` D-4）建议超级管理员。
- BP 下 `winner_team_id` 是否允许为空？（`docs/permissions.md` D-6）建议允许。
