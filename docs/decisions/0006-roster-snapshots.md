# ADR-0006：开赛即锁定并快照名单

- 状态：已接受（2026-09-29 经产品负责人确认）
- 日期：2026-09-29
- 相关：规范第 2.10、6.4、9.4、10.7 节；`docs/schema.md` 第 8 节

## 背景

规范反复强调"不要让当前数据改写历史"。具体到一场辩论，最容易出事的地方是：比赛结束后，学生改了显示名、被调到别的队伍、或评分被修改，导致那份已经发布的 ballot 上显示的名单和当时不一致。

规范第 2.10 节与第 9.4 节给出了解法：裁判点击"开始辩论"时，名单锁定并生成快照。

## 决定

1. 裁判点击 **Start Debate** 时，调用一个数据库函数，在**一个事务内**同时：
   - 校验该裁判确实被指派到这场比赛；
   - 校验名单仍满足该赛制的人数要求；
   - 向 `match_roster_snapshots` 写入当时的学生显示名、队伍标签、位置、发言位、评分快照、是否 ironman；
   - 设置 `matches.started_at` 与 `roster_locked_at`，状态改为 `started`；
   - 写审计记录。
2. 该操作**幂等**：重复点击不会生成第二份快照，而是返回既有状态。
3. `match_roster_snapshots` **只追加**：对客户端角色没有任何 INSERT/UPDATE/DELETE 权限，只能由该函数写入。
4. 此后 ballot 的一切呈现（包括已发布版本）都读取快照，而不是读取当前的 `teams`/`profiles`。
5. 开赛后的名单修复必须走**专门且审计的紧急更正流程**，绝不直接改快照（规范第 10.7 节）。

## 影响

**变简单：**
- 历史 ballot 永远与当时事实一致，不会因为后续档案修改而变化；
- 学生改名、转队、评分调整都不影响已完成的辩论；
- 审计与快照互相印证。

**变复杂：**
- 开赛前如果有人退赛，必须**在开赛前**处理；开赛后就需要走紧急流程；
- 快照表会随比赛数量增长（属于正常的历史数据，不是冗余）；
- 需要明确区分"读快照"与"读当前值"的代码路径，避免混用。

## 备选方案

- **不加快照，靠审计日志重建历史。** 重建复杂、易错，且审计日志是给管理员看的，不适合作为渲染数据源。否决。
- **用数据库时态表（temporal table）统一处理历史。** 对一个非技术负责人维护的项目来说过重。否决。

## 待确认

- 开赛后的"紧急名单更正"具体允许哪些改动、由谁批准？（规范第 17 节列为待确认，`docs/permissions.md` 无对应项）
- 裁判 paradigm 是否同样在开赛时快照？（`docs/schema.md` S-8）建议是。
