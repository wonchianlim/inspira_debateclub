# ADR-0005：配对与裁判推荐使用确定性启发式算法

- 状态：已接受（2026-09-29 经产品负责人确认）
- 日期：2026-09-29
- 相关：规范第 2.1、10、11 节；`docs/schema.md` 第 8 节

## 背景

规范第 10 节明确："V1 使用透明的确定性启发式算法，不是机器学习。系统提出建议，管理员确认。"

同时规范第 9.3 节要求："持久化提案的输入、分数、警告与算法版本，让管理员能理解为什么给出这个建议。"

## 决定

### 1. 算法性质

- 纯函数式的确定性计算，不含随机性、不含机器学习；
- 权重按规范第 10.3、10.4、11 节给定（队伍成本、比赛成本、裁判成本）；
- **低分更优**。

### 2. 确定性来源

- 排序时使用稳定键：先按 `rating_snapshot`，再按学生 UUID；
- 正反方/位置分配在分数相同时，使用**基于事件 ID 与队伍 ID 的种子哈希**决定（规范第 10.5 节），保证输入不变则结果不变。

### 3. 人工优先

- 管理员的手工改动一律审计；
- **重新生成时必须保留已锁定/手工调整的分配**，除非管理员显式解锁（规范第 10.7 节）；
- 已开赛的比赛名单永久锁定。

### 4. 可解释性

- 每个提案持久化：输入快照、各候选的分数、触发的警告、算法版本号；
- 界面展示"理由与警告"，而不是只显示一个不透明的分数（规范第 13 节）。

### 5. 硬约束 vs 软权重

资格不符与不可用属于**硬约束**，在正常生成时直接排除；规范给出的巨大权重（1000、500）用于**例外与人工分析场景**时仍能表达优先级。这一点必须在实现中区分清楚，否则会出现"算法推荐了不合格学生"的情况。

## 影响

**变简单：**
- 同样的输入永远得到同样的结果，测试可以断言精确输出（规范第 10.8 节）；
- 管理员可以复现"为什么上周是这么分的"；
- 不需要训练数据或模型运维。

**变复杂：**
- 权重是否合理需要用真实数据验证，可能需要在 Phase 4 之后调整；
- 全局优化（规范第 10.2 节要求"全局优化而非贪心"）的实现比贪心复杂，需要明确的算法说明文档；
- BP 的四队赛制需要额外处理（同时考虑房间整体均衡与相邻队伍强度，不能简化为二元胜负）。

## 备选方案

- **随机或机器学习配对。** 规范第 10 节明确排除。
- **纯人工配对，系统只做展示。** 不满足规范第 1.1 节的"系统能为每种启用的赛制提出可行的队伍与比赛"，且无法减少人工工作量。

## 待确认

- 权重取值是否需要用真实历史数据校准？（建议 Phase 4 完成后用一次真实活动验证）
- 规范第 10.2 节的"最小化管理员警告/改动次数"目标如何度量，需要产品负责人给出可接受的警告数量预期。
