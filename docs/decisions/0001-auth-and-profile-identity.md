# ADR-0001：认证服务与档案身份合并为一个 UUID

- 状态：已接受（2026-09-29 经产品负责人确认）
- 日期：2026-09-29
- 相关：规范第 6.1 节、第 7 节；`docs/permissions.md` 第 2 节

## 背景

系统需要一种可靠方式回答"当前请求是谁发出的"，因为所有权限判断都以此为起点。规范第 6.1 节建议档案 UUID 与认证服务的用户 UUID 相同，以简化 RLS。

## 决定

- `profiles.id` 直接等于认证服务的用户 UUID，并以外键引用它；
- 用户注册时由数据库触发器自动创建对应的 `profiles` 行，客户端不直接插入；
- 角色存放在独立的 `user_roles` 关联表，一个账号可拥有多个角色；
- 数据库中的"当前用户"通过 `auth.uid()` 获得。

## 影响

**变简单：**
- 权限策略可以直接写"这一行属于当前用户"，不需要额外的连接；
- 不需要维护"认证账号"与"业务档案"之间的同步逻辑；
- 越权测试可以用真实身份直接连接数据库执行。

**变复杂：**
- 数据库结构从此**绑定**到所选认证服务。如果最终换成"同区域托管 PostgreSQL + 自建认证"（规范第 5.1 节备选方案 2），`profiles` 及其全部外键关系都需要改写，这是主要的迁移成本；
- `profiles.email` 与认证服务里的邮箱重复，变更时需要同步；
- 用户不能物理删除，否则会破坏审计与历史（见 `docs/schema.md` S-16）。

## 备选方案

1. **档案使用独立主键，另设 `auth_user_id` 列。** 更灵活，可以在不改业务表的前提下更换认证方案。代价是每个策略都要多一次间接引用，复杂度更高。考虑到规范第 1.2 节明确排除微服务和过度设计，未采用。
2. **自建认证。** 不做，因为规范第 5.1 节明确说对一个非技术负责人来说自托管不是默认选项。

## 待确认

- 新注册账号的默认角色是什么？（`docs/permissions.md` D-1）。建议默认 `student`，裁判注册后进入待批准状态。
- 不活跃账号采用停用 + 匿名化，而非物理删除——需要产品负责人确认（`docs/schema.md` S-16、D-2）。
