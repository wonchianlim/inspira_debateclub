# ADR-0008：使用 npm 作为包管理器

- 状态：提议
- 日期：2026-09-29
- 相关：规范第 5.1 节、第 14.1 节

## 背景

规范第 5.1 节要求"锁定版本在 package lockfile 中"，第 14.1 节要求"使用仓库自己的包管理器和脚本"运行检查。因此必须明确选定一个包管理器，并让所有命令与文档保持一致。

本机现状：已安装 Node.js 与 `npm`；`pnpm` 未全局安装，但开发环境（DSH 运行时）自带一份位于其自身安装目录下的 `pnpm`。

## 决定

使用 **npm**：

- 版本精确写死在 `package.json`（不使用 `^` 或 `~`）；
- 提交 `package-lock.json` 作为唯一版本依据；
- CI 与本地统一使用 `npm ci` 安装，保证结果一致。

## 影响

**变简单：**
- 不需要额外安装任何全局工具，减少一个环境依赖；
- 对非技术负责人而言，遇到问题时 `npm install` 是最容易搜到答案的命令；
- 不依赖 DSH 自带的 `pnpm` 路径——该路径会随 DSH 更新而变化，不适合作为长期项目的构建基础。

**变复杂：**
- 相比 `pnpm`，安装更慢、磁盘占用更大，且依赖结构更扁平；
- 若将来改用 `pnpm`，需要重新生成 lockfile 并在 CI 中同步替换命令（属机械改动，不影响应用架构）。

## 备选方案

- **使用 DSH 内置的 pnpm。** 会引入一个位于第三方应用安装目录内的路径依赖，DSH 升级后可能失效。对一个要长期维护的项目不合适。
- **全局安装 pnpm。** 需要改动系统级环境，属于规范要求先取得同意的操作，且收益有限。

## 待确认

- 产品负责人是否同意使用 npm（`docs/architecture.md` A-1）。这是可逆的细节决定，若不特别指定，将按本 ADR 执行。
