# ADR-0007：认证调用经自有域名转发

- 状态：提议
- 日期：2026-09-29
- 相关：规范第 1.1、5.2、5.4 节；`docs/architecture.md` 第 8 节

## 背景

两条规范要求在这里汇合：

1. 第 5.4 节要求生产浏览器体验**不得**依赖未经大陆测试的境外域名（点名 Google Fonts、公共 CDN、分析、CAPTCHA 等）；
2. 第 5.2 节要求"尽可能让浏览器只与应用自有域名通信"。

而认证是整个系统里**最不能失败**的一步：如果学生打不开登录页或无法刷新会话，其他功能都没有意义。默认做法（浏览器直连认证服务的域名）恰好把一个境外域名放到了最关键路径上。

## 决定

1. 注册、登录、登出、忘记密码、重置密码全部通过 **Server Action** 执行，浏览器只向自有域名发请求；
2. 会话刷新在 `middleware.ts` 中于服务端完成，使用 `getUser()` 向认证服务核实（**不用**只读 cookie 的 `getSession()` 做授权判断）；
3. 认证服务发出的邮件链接**必须**改写为指向自有域名的地址（`{NEXT_PUBLIC_APP_URL}/auth/confirm?...`）；
4. 认证服务的"允许跳转地址"白名单只放自有域名；
5. 实现 `app/auth/confirm/route.ts` 在自有域名上完成验证并建立会话。

## 影响

**变简单：**
- 登录页本身是自有域名上的普通页面，即使认证服务一时不稳，页面仍能打开并给出可理解的提示；
- 失败可以被我们自己的日志记录和排查，而不是只能看浏览器控制台；
- 满足"生产页面不依赖境外第三方域名"的验收要求；
- 密码重置链接在大陆可打开——**这一点若不做，重置密码功能在大陆等于不可用**。

**变复杂：**
- 登录请求多一跳（浏览器 → 我们的服务器 → 认证服务），登录会稍慢；
- 必须记得在认证服务后台改邮件模板与跳转白名单，否则重置密码仍会指向境外域名；
- `middleware.ts` 需要正确配置，避免静态资源也走会话刷新而变慢。

## 备选方案

1. **浏览器直连认证服务。** 实现最简单，但把境外域名放进登录与每次会话刷新的关键路径，与第 1.1 节的"大陆可正常使用"验收标准直接冲突。否决。
2. **完全自建认证。** 规范第 5.1 节指出对非技术负责人来说自托管不是默认选择。仅在 Phase 0 连通性验证证明托管方案不可用时，才作为备选方案之一提出（见规范第 5.1 节的两种替代路径）。

## 待确认

- Phase 0 连通性测试必须**专门测试会话刷新**，而不只是首屏加载。若认证服务在新加坡而从大陆访问不稳定，则需按规范第 5.1 节提出替代方案。
- 认证服务的邮件模板与跳转白名单属于外部配置，必须在 Phase 1 纳入检查清单。
