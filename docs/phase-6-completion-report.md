## 4. ⚠️ 本阶段最重要的一件事：**实测发现学生可以冒签**

写签到动作时我注意到 `registrations` 上的 `registrations_update_own` 策略
允许学生更新**自己**的报名行 —— 而那行里还有 `check_in_method` 这一列。

实测确认：

```sql
update registrations set checked_in_at = now(),
                         check_in_method = 'admin',
                         status = 'checked_in'
 where student_id = my_student_id();
→ 成功
```

**也就是学生可以把自己标成「管理员代签」。**

影响范围有限（只能改自己那一行），但它是**记录真实性的问题**：
签到方式存在的意义就是事后能分清"学生自己签的"与"管理员代签的"。
如果学生能自己写成 admin，这个区分在争议时就不成立了。

**修复：** 加触发器 `enforce_check_in_method`，
`check_in_method = 'admin'` 只能由管理员或 `service_role` 写入。
放在数据库层而不是应用层，因为这是"谁可以写入哪个值"的规则 ——
放在应用层的话，任何一处绕过（例如直接调用 PostgREST）都能写进去。

## 5. ⚠️ 又一次"假通过"，而且是**反向验证**抓出来的

我为上面那条修复写了用例 `F-STU-39`，加上触发器后它**通过**了。

**但反向验证（去掉触发器）时它照样通过** —— 说明那条用例**什么都没验证**。

原因：我写的是**裸 `update`**，而它不返回任何行。
用例断言"拒绝"，运行时因为**没东西可数**而报 `DENIED`，
与"被触发器拦住了"在结果上**一模一样**。

改成 `with x as (update ... returning 1) select count(*) from x` 之后，
反向验证才真正失败（`ROWS=1`），修复也才真正被固定住。

> **这是本项目第四次遇到"假通过"，也是第一次由"反向验证"本身抓出来的。**
> 前三次分别是：P3-1 的子查询取到 NULL、P4-1 的发言位没占用、P4-5 的空表。
> 共同点始终是：**测试通过的原因和它想验证的事情无关。**

## 6. 比赛设置可配置（产品负责人的要求）

Phase 5 完成报告的 **L-7** 记录过：比赛时间与房间当时是写死的保守默认值。
产品负责人已明确要求"希望比赛时间和房间能自己设置"。

新增三项活动级配置：

| 列 | 含义 | 默认 |
|---|---|---|
| `events.match_start_at` | 第一场比赛开始时间 | 空 = **沿用活动开始时间** |
| `events.match_interval_minutes` | 每场间隔 | 60 |
| `events.room_names` | 可用房间列表 | 空 = **退回 A101 起的默认** |

**默认值刻意保持"和以前完全一样"**，这样已有活动的排法不会因为这次改动悄悄变化。
界面上也写明：**只影响以后重新生成的比赛**。

房间名在保存时会**自动去重** —— 因为 `matches` 上有"同一活动内房间名唯一"的约束，
重复会直接违反约束，而那条错误信息对管理员毫无意义。

## 7. 两处规范要求做成了**结构性**的

1. **"颜色只是展示层，数据库存语义状态"** —— 领域层只输出六个语义值
   （`neutral/warning/ready/live/complete/cancelled`），不输出任何颜色或样式类名。
   另有一个 `liveStateUrgency()` 映射"要不要立刻处理"，**仍然不是颜色**。
2. **"从时间戳算，不依赖浏览器假设"（第 17 节）** —— 模块**只接受时间戳**，
   "现在"由调用方传入。这也正是边界测试能写出来的原因：
   恰好警告时刻、恰好开始前 30 分钟、恰好开始时间，**三条边界都有测试**。

另外规范里一处容易读漏的细节也照做了：
**`ready` 要求学生与裁判都到齐** —— 学生全到了但裁判没到**不算** `ready`。
